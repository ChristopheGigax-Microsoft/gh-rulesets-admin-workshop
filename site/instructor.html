Facilitator only / Delivery and recovery

Teach the decision behind the toggle.

Agree the repository and scope

  1. Obtain owner authorization to use an existing customer repository or an optional disposable repository. Confirm supported plan/visibility, exact exercise refs, and cleanup expectations. A new project or template is not required. Do not create repositories or blanket rules as an unannounced side effect of setup.
  2. In an existing repository, preserve application files, workflows, default-branch protections, and unrelated rules. Agree a harmless practice-file path. If participants share the repository, allocate unique refs/ruleset names to each solo participant or pair and adapt all snippets and JSON bodies.
  3. Confirm participant admin access. A partner is optional; solo participants perform the actions themselves. If paired, confirm accepted reviewer write access under customer policy. GitHub does not allow PR authors to approve their own PRs: use Lab 3's solo route rather than requiring a second person or account.
  4. Review inherited organization/enterprise rules and legacy branch protection. Check which isolated direct-update experiments are permitted on the agreed refs. Never weaken existing or parent policy; record blocked exercises or arrange an authorized demonstration.
  5. Verify Git auth and branch/tag trigger safety, including existing automation. Workshop refs must not deploy or publish releases. For Lab 4's optional example, verify Actions/action allowlists, an approved runner, pinned checkout, and Node.js 22+. It does not request secrets.
  6. Choose safe existing customer CI or the complete optional Lab 4 code example. Rehearse baseline green and meaningful failure/correction, recording the actual check/source. Install the example through an approved PR into the integration branch, not by requiring a starter folder or default-branch setup commit.
  7. Check compatible squash/rebase methods for linear-history practice; change repository-wide merge settings only with owner approval. Verify the supported PR-only bypass mode and approval for its temporary admin-role grant before making lab 7 a participant exercise.

Facilitate the progression

Begin with effective-policy inspection, not a screen tour. For every lab, ask for a prediction before the attempt and an explanation after the rejection. Keep the configuration actor and operation actor explicit. Solo participants configure and challenge their own policy; optional pairs can alternate reviewing without sharing credentials. Solo is a supported route, not a failed pairing prerequisite.

Lab 3's solo route proves the missing-approval blocker and conversation resolution, then explicitly returns only its workshop-created rule to zero required approvals for later CI work. Counted approvals and stale-approval dismissal remain not exercised. Lab 7 can prove bypass removal solo by leaving the second PR blocked; its normal approved merge is optional. Do not describe a self-inspection or a lowered approval count as independent approval evidence. Existing/inherited review requirements are never relaxed to enable solo work.

Use exact targets for core experiments: integration, destructive, layering, bypass, capstone, and workshop-version tags. The first lab explores patterns only while disabled. The later separate refs avoid stacking unrelated blockers on every exercise.

Lab 4 accepts existing customer CI or optional PR-title validation, not necessarily a build. For the title route, demonstrate baseline green, edited-title red with blocked merge, corrected-title green on the same head, and revalidation after code pushes. Customer CI follows the equivalent genuine failure/recovery evidence contract. Explain why Conventional Commits applies to commit messages and what adopting its header for PR titles does not guarantee.

Required live rehearsal before delivery

Verification boundary.

The course's local checks validate source, links, examples, and validator behavior. They do not prove GitHub enforces a live rule. Until the following is executed on explicitly authorized workshop refs, live enforcement is unverified. Do not present an unperformed rehearsal as completed.

  1. Record actual plan, visibility, inherited rules, participant admin actor, solo/paired route, reviewer write actor if present, Actions availability, and absence of matching bypass grants.
  2. Complete preflight's harmless baseline PR, satisfying existing checks and any existing review requirements. No extra partner approval is required for solo preflight. For Lab 4, select customer CI or install its optional workflow/validator through the approved setup PR; verify fresh check runs on a subsequent practice PR.
  3. Perform lab 2's rejected direct update and normal PR merge; independently prove deletion and actual non-fast-forward rejection on the disposable branch.
  4. Reproduce Lab 3's solo missing-review blocker and unresolved/resolved thread sequence, including the declared transition back to zero approvals in its own rule. If delivering the optional paired route, also rehearse counted approval, dismissal after a real diff change, and renewed approval with an eligible reviewer. Otherwise leave those cases explicitly unverified.
  5. For lab 4, require the exact actual check/source. Test valid-to-invalid and invalid-to-valid title edits on the same head commit, inspect fresh runs, and confirm merge-box state after each. Also push a diff-changing commit and verify current-title validation. If using customer CI, record its meaningful failing input and recovery.
  6. Reproduce the two-parent merge rejection and identical-update success with only the linear overlay disabled; verify baseline deletion protection remains.
  7. Reproduce tag creation, mutation/deletion rejection, unchanged object identity, and next-version creation without any downstream release/deployment.
  8. Reproduce Lab 7's explicit PR-only exception, persistent direct-push block, removed exception, and restored review block. Solo rehearsal ends with that block and an export; rehearse a compliant reviewed merge only if delivering the optional reviewer path.
  9. Run one capstone policy challenge with distinct allow/deny evidence for each chosen control. Compare final exports with the UI. Rehearse cleanup.

When a checkpoint is blocked

Capture the real blocker and separate missing capability from incorrect configuration. Use the diagnosis guide. If inheritance prevents a core isolation experiment, record participant execution as blocked or show an authorized facilitator demonstration. An optional separate repository may be used only if the customer agrees; it is not required to use the workshop. A demonstration is not participant evidence. Do not silently downgrade an Enterprise exercise into a different capability and label it complete.

Answer key and final review

Use the observable-outcome table rather than a single prescribed settings screenshot. Ask each participant to identify scope, source, bypass, check identity, and a recovery path. For the capstone, require at least three justified controls including actual CI, successful self-executed or optional partner challenges, a compliant merge, and a matching export. A solo policy can use PRs, CI, and deletion protection without independent approval. Record the route and actor roles; never claim optional approval cases passed when not exercised.

Cleanup and durable handoff

  1. Agree which workshop-created refs, files, workflows, and policies to retain or remove. Save approved evidence and final exports before altering protections. An existing customer repository and its unrelated contents must remain intact; never delete the whole repository automatically.
  2. Remove temporary bypass grants first. Keep the agreed final integration/capstone policy active on retained workshop refs. Remove optional CI example files only through the approved contribution path, after removing workshop-only check requirements and confirming no retained refs depend on them.
  3. For disposable refs scheduled for cleanup, disable only the exact workshop-created destructive/layering/bypass/tag rule that prevents their deletion. Confirm no shared or parent policy is being edited.
  4. Delete only the explicitly inventoried disposable workshop branches and tags in the approved repository using the UI or exact ref names. Do not use wildcard bulk deletion, broad resets, or force pushes on default/shared refs.
  5. Remove only workshop-granted temporary partner write access when it is no longer needed, following organizational policy; preserve pre-existing access. An organization-level extension needs the authorized facilitator to remove its temporary parent rule.
  6. Reinspect retained effective policy, actor access, and exports. Record complete, blocked, and skipped modules separately. Optional browser-local progress can be cleared independently of the actual evidence.

Static handoff

Upload only the contents of site to the approved static host, preserving relative paths. No course-site deployment workflow is included. Check the real host behavior; do not assume an unverified platform contract. The embedded examples stay available without access to the source repository.
